# ADR-0006 · 文档元数据、权限与软归档

- 日期：2026-10-21
- 状态：M1.4 提案；本地实现，待人工审查及远程 CI

## 背景

Document 已包含本阶段全部字段与唯一 room 约束；M1.2 Session 和 M1.3 WorkspaceAccess / 父行锁提供真实身份及成员撤权协议。当前需求是元数据 CRUD，正式正文协作属于 M2，不能借用 M0 公共演示房间代表私有文档。

## 决定

1. 保留 Schema 与所有历史 Migration。API 挂在空间路径下；所有查询限定 workspaceId，详情和更新再限定 documentId 与 archivedAt=null。读取事务使用 RepeatableRead，使成员验证与元数据处于同一快照。
2. 复用 SessionGuard 和来源校验。OWNER / EDITOR 可写、VIEWER 可读；匿名 401、角色不足 403、非成员 / 缺失 / 跨空间 / 已归档 404。公开 DTO 仅 select id、workspaceId、title 和时间；标题白名单校验后去首尾空白。
3. 写事务使用 ReadCommitted，先锁 Workspace 父行，再重新校验成员角色。与成员变更共用锁协议，保证排队期间被撤权的写者不能沿用旧权限。改名和归档使用未归档条件更新及行数检查，不提供重新启用路径。
4. 归档只设置 archivedAt，保留全部快照与关联数据；详情、改名和重复归档统一 404。当前不实现恢复和物理删除。
5. 服务端生成 `doc:${randomUUID()}`，现有唯一约束处理极端冲突。仅对 room 的 P2002 最多尝试三次，每次独立事务；耗尽返回 409。room 不是授权凭据，不在公开 DTO 中返回。
6. React 在 WorkspacePanel 内管理真实元数据，按用户 / 空间 / 角色隔离组件，请求序号防止迟到响应覆盖新选择；401 清理会话，403 隐藏失效写入口，404 清理详情。真实文档不创建协作 provider，正文入口明确留给 M2。

## 取舍与限制

- 单独锁 Document 可减少同空间不同文档的竞争，但无法与现有成员撤权锁建立一致顺序。本阶段沿用空间锁，操作短小且边界明确；同空间写入串行化，尚未压测，不为高频正文写入复用此入口。
- 归档 / 改名单独依赖先读后写会产生竞态，采用父行锁并保留条件更新作为最终检查。直接 SQL、脚本和未来写入口需遵守同一协议；数据库未建立跨业务授权约束。
- 已开始的合法读取可在并发撤权后完成；不承诺撤回已发响应。每个新请求重新验证会话和成员。前端没有实时成员推送，短暂旧界面不能绕过服务端写权限。
- 元数据列表暂无分页；写入成功后刷新列表，多一次读取以保持排序和归档状态准确。失败后显示可重试错误，网络中断时服务器可能已提交，需刷新确认。
- 没有新增依赖、通用权限框架或存储协议。Yjs binary、Hocuspocus 鉴权和生产部署继续按 M2 门槛处理。

## 验证

真实 HTTP + PostgreSQL 16 集成覆盖权限矩阵、隔离、输入、会话、二进制快照保留、唯一冲突重试与耗尽，以及通过锁等待门闩确定顺序的归档 / 改名和成员降级竞态。Playwright 覆盖真实 API 管理、只读权限、空间 / 文档迟到响应、断网恢复、401 / 403 / 404、账号隔离和桌面 / 移动布局；结果以 [M1.4 报告](../reports/M1.4.md) 为准。
